# 02 — RPC 协议帧层：帧格式设计与粘包/拆包处理

---

## 一、为什么需要协议帧层？

### 序列化层的输出是一串字节，但这串字节本身不完整

v0.1 的 `Serializer` 能把 `Add(3, 5)` 的两个参数编码成 14 字节的二进制数据。但这 14 字节只包含**参数数据**，缺失了关键信息：

- **这是哪个请求？** — 客户端可能在同一个 TCP 连接上连续发 3 个请求，服务端需要知道哪个响应对应哪个请求
- **调用哪个方法？** — 服务端可能提供 `Add`、`Sub`、`Mul` 等多个方法
- **这是一个请求还是响应？** — 消息类型需要区分
- **消息从哪开始、到哪结束？** — TCP 是字节流，没有消息边界

**协议帧层的唯一目的：在序列化后的参数数据外面包一层"信封"，告诉接收方这封信是谁、干什么、有多长。**

---

## 二、核心问题：TCP 粘包与拆包

这是面试必考题，必须彻底理解。

### TCP 是一个字节流，不是消息流

```
发送端调用了三次 send：
  send("ABC")
  send("DEF")
  send("GHI")

接收端 recv 可能收到：
  情况 A: "ABCDEFGHI"        ← 三条消息粘在一起（粘包）
  情况 B: "ABCDEF" + "GHI"   ← 部分粘、部分拆
  情况 C: "ABC" + "DEFG" + "HI"  ← 任意切分
```

TCP 只保证**字节顺序不变、最终全部到达**，不保证**消息边界与发送边界一致**。这个跟你在 HTTP 服务器里遇到的问题性质相同——你用 `\r\n\r\n` 分隔 HTTP 头，RPC 没有这个奢侈的条件（二进制数据中任意字节都可能等于 `\r`）。

### 解决方案：长度前缀法（Length-Prefixed Framing）

在每一条消息前面写一个**固定长度的头部**，头里包含**消息体的长度**。接收方先读固定长度的头，从头里知道消息体有多长，再精确读消息体。

```
┌──────────────────┬─────────────────────────────┐
│  固定长度帧头      │  变长消息体（payload）        │
│  (N bytes)        │  (Length 字段指定的字节数)     │
└──────────────────┴─────────────────────────────┘
```

接收方状态机：

```
[等待帧头] → 收到 N 字节 → 解析帧头，提取 Length
  → [等待消息体] → 收到 Length 字节 → 完整消息到达，交给上层处理
  → [等待帧头] → ...循环
```

这是 TCP 应用层协议最基础、最通用的解决方案。HTTP 的 `Content-Length` 头、WebSocket 的帧格式、几乎所有二进制协议都在用这个思路。

## 三、帧格式设计

### 完整帧布局

```
┌─────────┬──────────┬───────────┬───────────┬──────────┬──────────┬──────────────┐
│ 魔数     │ 总长度    │ 请求 ID    │ 消息类型    │ 方法名长度 │ 方法名     │ 序列化 body   │
│ 2 bytes  │ 4 bytes   │ 4 bytes    │ 1 byte     │ 2 bytes   │ N bytes   │ M bytes       │
└─────────┴──────────┴───────────┴───────────┴──────────┴──────────┴──────────────┘
 ←────────── 固定帧头 13 字节 ──────────→ ←────────── 可变部分 ──────────────→
```

### 各字段详解

**魔数（Magic Number）— 2 字节**

```
固定值：0xBABE（43710）
```

作用：快速识别一段字节流是否合法帧。接收方读到的前 2 字节如果不是 `0xBABE`，说明对端发来的不是你的协议（可能是错连了端口或数据损坏）。

为什么选 `0xBABE`？任意选一个不容易随机撞上的值即可，无特殊含义。HTTP/2 用 `PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n`（24 字节的"魔数字符串"），二进制协议通常用 2-4 字节的魔数。

**总长度（Total Length）— 4 字节，网络序（大端）**

```
总长度 = 帧头固定部分（13 字节）+ 方法名字节数 + body 字节数
```

这是解决粘包/拆包的核心字段。接收方读完帧头后，用 `总长度 - 13 - 方法名长度` 算出 body 的精确字节数，精确读取。

**请求 ID（Request ID）— 4 字节，网络序**

```
每个请求分配一个唯一 ID（单调递增即可）
```

作用：TCP 连接是异步全双工的。客户端可以在同一个连接上连续发 3 个请求（ID=1,2,3），服务端可能先生成 ID=2 的响应再生成 ID=1 的响应（线程池调度的原因）。客户端靠请求 ID 把响应匹配回请求。

```
客户端发送：         服务端处理：          客户端收到：
  req id=1  ──→      线程A处理 id=1(慢)
  req id=2  ──→      线程B处理 id=2(快)  →  resp id=2 ✓ 匹配！
  req id=3  ──→      线程C处理 id=3(中)       resp id=1 ✓ 匹配！
                                              resp id=3 ✓ 匹配！
```

**消息类型（Message Type）— 1 字节**

| 值 | 含义 |
|----|------|
| 0x01 | 请求（客户端 → 服务端） |
| 0x02 | 响应（服务端 → 客户端） |
| 0x03 | 错误（服务端 → 客户端，执行失败） |

**方法名长度（Method Name Length）— 2 字节，网络序**

```
方法名长度 = 紧跟着的"方法名"字段的字节数
```

为什么不把方法名长度写死在帧头里？因为方法名是可变长的——`"Add"` 是 3 字节，`"UserService.GetUserById"` 是 24 字节。必须先知道长度才能精确读取。

**方法名（Method Name）— N 字节**

```
如 "Add"、"Mul"、"UserService.GetUser"
```

服务端依据方法名在注册表中查找到对应的 C++ 函数。

**序列化 body — M 字节**

```
由 v0.1 的 Serializer 编码的参数数据（请求时）或返回值数据（响应时）
```

帧层完全不解包 body 的内容——它只负责把 body 完整地传给 Serializer，由 Serializer 来解释。这就是**分层解耦**。

## 四、帧编码与解码流程

### 编码（客户端发起调用时）

```
输入：方法名 "Add"、请求 ID=1、参数 body（14 字节）

1. 计算总长度：13 + strlen("Add") + 14 = 30
2. 写入魔数：0xBA, 0xBE
3. 写入总长度：HostToNetwork32(30)
4. 写入请求 ID：HostToNetwork32(1)
5. 写入消息类型：0x01
6. 写入方法名长度：HostToNetwork16(3)
7. 写入方法名："Add"（3 字节）
8. 写入 body：14 字节序列化数据

输出：30 字节完整帧 → 交给 TCP socket send
```

### 解码（服务端接收数据时）

采用**状态机**分两步读：

```
状态 1：等待帧头（13 字节）
  ↓ 收到 ≥ 13 字节
  → 读魔数，校验是否为 0xBABE
  → 读总长度（TotalLen）
  → 读请求 ID
  → 读消息类型
  → 读方法名长度（MNameLen）
  → 切换到状态 2，等待 (TotalLen - 13) 字节

状态 2：等待消息体（TotalLen - 13 字节）
  ↓ 收到 ≥ (TotalLen - 13) 字节
  → 读方法名（MNameLen 字节）
  → 读 body（TotalLen - 13 - MNameLen 字节）
  → 完整帧就绪，交给上层 Dispatch
  → 切换回状态 1，等待下一个帧头
```

### 核心数据结构：Buffer

接收方需要一个缓冲区来处理"此次 recv 只收了不完整的帧"的情况：

```
class Buffer {
    std::vector<uint8_t> data_;
    size_t read_pos_;

    // 从 socket fd 读取数据追加到缓冲区
    ssize_t ReadFromFd(int fd);

    // 尝试解析一个完整帧
    std::optional<Frame> TryDecode();

    // 丢弃已解析的数据，释放缓冲区空间
    void Consume(size_t bytes);
};
```

缓冲区设计的关键：
- `ReadFromFd` 总是追加到末尾，不覆盖未解析的数据
- `TryDecode` 检查是否有足够字节构成完整帧。不够 → 返回 `nullopt`，继续 recv
- `Consume` 清掉已解析的部分，避免缓冲区无限增长

## 五、错误处理

帧层可能遇到的异常情况比序列化层多：

| 错误 | 检测方式 | 处理 |
|------|----------|------|
| 魔数不对 | 读帧头时前 2 字节 ≠ 0xBABE | 关闭连接（对端不是本协议或不合法） |
| 总长度异常大 | 总长度 > 合理上限（如 10MB） | 关闭连接（防止内存耗尽攻击） |
| 总长度异常小 | 总长度 < 13（比帧头还小） | 关闭连接 |
| 帧不完整 | 缓冲区字节数 < 总长度 | 继续等待 recv（正常情况，不是错误） |
| 方法名长度异常 | MNameLen > 总长度 - 13 | 关闭连接 |
| 消息类型未知 | 不是 0x01/0x02/0x03 | 关闭连接 |

**设计原则：信任客户端发送的数据在格式上可能是恶意的，任何不符合协议的帧都应导致连接关闭。**

## 六、与序列化层的关系

帧层只负责**消息边界和元信息**，序列化层负责**参数数据的编解码**。它们通过 body 字段连接：

```
帧层编码时：
  调用 Serializer 编码参数得到 body 字节序列
  → 把 body 放入帧的 payload 位置

帧层解码时：
  从帧中提取 body 字节序列
  → 传给 Serializer 解码得到 C++ 对象
```

**关注这个解耦设计**：帧层不关心 body 里面是什么（TLV？JSON？Protobuf？），序列化层不关心数据是怎么传输的（TCP？UDP？文件？）。两层各司其职，可以各自独立演进。

## 七、v0.2 实现范围

### 要做

- `ProtocolFrame` 类：编码/解码帧
- `Buffer` 类：管理接收缓冲区，处理粘包/拆包状态机
- 帧层单元测试：正常编解码往返、不完整帧、魔数错误、长度异常、多次 recv 模拟粘包

### 不做

- 不实现请求 ID 的分配和匹配（属于 v0.5 Stub/Dispatch 层）
- 不实现消息类型 0x03（错误帧）的完整处理（先定义，实际逻辑在 v0.5）
- 不实现超时重传（属于传输可靠性，后续版本）

### 涉及的新类型

需要在 `common.h` 中新增一个 `MessageType` 枚举：

```cpp
enum class MessageType : uint8_t {
    Request  = 0x01,  // 请求
    Response = 0x02,  // 正常响应
    Error    = 0x03,  // 错误响应
};
```

以及一个 2 字节的 `HostToNetwork16` / `NetworkToHost16` 用于方法名长度字段。

## 八、面试重点

这一层能聊的核心话题：

1. **TCP 粘包/拆包的本质**：TCP 是字节流，不是消息流。应用层必须自己切分消息边界。
2. **长度前缀法 vs 分隔符法**：为什么二进制协议不用 `\r\n` 分隔？（二进制数据可能包含任意字节）
3. **帧头设计取舍**：为什么魔数用 2 字节而不是 4 字节？（节省带宽 vs 误识别概率的权衡）
4. **缓冲区管理的边界条件**：如果攻击者发送了一个声称 10GB 的帧，你的代码怎么处理？
5. **分层解耦**：帧层和序列化层怎么协作？如果将来把 TLV 换成 Protobuf，帧层需要改哪些代码？（答案：0 行）
