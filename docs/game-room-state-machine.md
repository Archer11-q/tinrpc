# 游戏房间状态机设计

## 一、为什么需要状态机？

游戏房间的生命周期不是线性的。一个房间从创建到销毁，会经历多个阶段：

```
玩家创建房间 → 等待其他玩家加入 → 人满开始游戏 → 游戏结束结算 → 房间销毁
```

如果不用状态机、只靠几个 `bool` 标志位（`is_waiting`、`is_playing`、`is_finished`），会出现这样的问题：

```cpp
// ❌ 标志位方案 — 状态组合爆炸
if (is_waiting && !is_playing && player_count >= 2) {
    // 应该开始游戏
}
// 但如果有人同时点了"开始"和"离开"？标志位之间没有互斥保证。
```

**状态机强制房间在同一时刻只处于一个状态**，每次状态转换有明确的前置条件。非法操作（如在"等待中"的房间里直接发"结算"）会被状态机直接拒绝。

---

## 二、状态定义

房间共有 **5 个状态**：

| 状态 | 含义 | 房间此时的行为 |
|------|------|--------------|
| `IDLE`（空闲） | 房间刚创建，尚未对外开放 | 等待房主确认开放 |
| `WAITING`（等待中） | 对外开放，接受玩家加入 | 接受加入请求，拒绝离开请求（房主除外） |
| `PLAYING`（游戏中） | 游戏正在进行 | 拒绝加入/离开，接收玩家输入帧 |
| `FINISHED`（结算中） | 游戏结束，展示结果 | 广播结算数据，等待玩家确认 |
| `DESTROYED`（已销毁） | 房间生命周期结束 | 清理资源，从 RoomManager 移除 |

对应 `proto/game.proto` 中的枚举（实现阶段会设计为 `RoomStatus`）：

```protobuf
enum RoomStatus {
    ROOM_STATE_IDLE       = 0;  // 空闲
    ROOM_STATE_WAITING    = 1;  // 等待中
    ROOM_STATE_PLAYING    = 2;  // 游戏中
    ROOM_STATE_FINISHED   = 3;  // 结算中
    ROOM_STATE_DESTROYED  = 4;  // 已销毁
}
```

> 注意：当前 `proto/game.proto` 的 `RoomStatus` 只有 4 个值（UNSPECIFIED/WAITING/PLAYING/FINISHED），实现 v0.8 时需要扩展为 5 个（加入 IDLE）。

## 四、状态转换条件详解

### 4.1 IDLE → WAITING（空闲 → 等待中）

**触发条件**：房主调用"确认开放"（或房主加入房间 — 取决于具体设计）。

**前置条件**：
- 房间处于 `IDLE` 状态
- 房主已在房间内

**转换动作**：
- 状态设为 `WAITING`
- 开始计时器：**空闲超时 5 分钟**（若期间无玩家加入，自动销毁）
- 对外通知：房间可被搜索和加入

### 4.2 WAITING → PLAYING（等待中 → 游戏中）

**触发条件**：房主调用 `StartGame`。

**前置条件**：
- 房间处于 `WAITING` 状态
- 当前人数 ≥ 2（最少需要 2 个玩家）
- 所有玩家都已 `ready`（就绪）
- 发起者是房主

**失败情况**：
- 人数不足 → 返回错误 "至少需要 2 人才能开始游戏"
- 有玩家未 ready → 返回错误 "请等待所有玩家准备"
- 非房主发起 → 返回错误 "只有房主可以开始游戏"

**转换动作**：
- 状态设为 `PLAYING`
- 取消等待超时计时器
- 锁定房间（拒绝新玩家加入、拒绝玩家离开）
- 广播 `OnGameStart` 通知给所有玩家
- 启动帧同步管理器（v0.9 实现）

### 4.3 PLAYING → FINISHED（游戏中 → 结算中）

**触发条件**：游戏逻辑判定结束（如一方胜利、达到时间上限、所有玩家完成回合）。

**前置条件**：
- 房间处于 `PLAYING` 状态

**转换动作**：
- 状态设为 `FINISHED`
- 停止帧同步
- 计算最终排名和分数
- 广播 `GameOverNtf` 给所有玩家
- 开始结算倒计时：**30 秒**

### 4.4 FINISHED → DESTROYED（结算中 → 已销毁）

**触发条件（满足任一）**：
- 所有玩家确认结算结果
- 结算倒计时超时（30 秒）

**前置条件**：
- 房间处于 `FINISHED` 状态

**转换动作**：
- 状态设为 `DESTROYED`
- 移除所有玩家
- 关闭所有连接（或通知玩家返回大厅）
- 从 `RoomManager` 移除自身
- 清理所有资源（定时器、缓冲区等）

### 4.5 任意状态 → DESTROYED（超时/强制销毁）

以下情况任一状态都可直接跳到 `DESTROYED`：

| 触发条件 | 适用状态 | 超时时长 |
|----------|---------|---------|
| 空闲超时 | `IDLE` | 5 分钟无操作 |
| 等待超时 | `WAITING` | 10 分钟无人加入 |
| 所有玩家离开 | `WAITING` | 立即（最后一个玩家离开后） |
| 房主主动关闭 | `WAITING` | 立即 |
| 结算超时 | `FINISHED` | 30 秒（已在 4.4 覆盖） |

## 五、超时策略汇总

| 状态 | 超时条件 | 时长 | 超时后动作 |
|------|----------|------|-----------|
| `IDLE` | 创建后未开放 | 5 分钟 | → `DESTROYED` |
| `WAITING` | 无人加入 | 10 分钟 | → `DESTROYED` |
| `WAITING` | 所有玩家离开 | 立即 | → `DESTROYED` |
| `FINISHED` | 展示结算结果 | 30 秒 | → `DESTROYED` |

> `PLAYING` 状态**不设超时**。游戏时长由游戏逻辑控制。若需防止单局过长，应在游戏逻辑层限制最大时长。

## 六、并发安全

游戏房间是**多玩家并发操作**的场景：

```
同一时刻可能发生：
  玩家 A 发送 "开始游戏"
  玩家 B 发送 "离开房间"
  超时计时器触发 "房间销毁"
```

### 6.1 设计原则

- **单线程模型**：所有房间状态变更由 `EventLoop` 所在的 IO 线程执行，不跨线程。状态变更天然串行，无需 mutex。
- **操作原子性**：每个状态转换函数检查当前状态 → 执行转换 → 更新状态，三步不可中断。
- **先检查后执行**：任何操作先校验"当前状态是否允许此操作"，拒绝非法请求。

### 6.2 典型竞态场景

```
场景：玩家 A 点开始游戏，同时定时器触发超时销毁

  线程 1（玩家 A）：WAITING → 检查人数 ≥ 2 → 准备切换到 PLAYING
  线程 2（定时器）：WAITING → 超时 → 准备切换到 DESTROYED

解决方案（单线程模型下自动解决）：
  EventLoop 单线程轮询，事件按到达顺序处理。
  先处理"开始游戏"→ 切换到 PLAYING → 定时器回调检查"当前状态不是 WAITING"→ 不执行销毁。
  先处理"超时"→ 切换到 DESTROYED → "开始游戏"回调检查"当前状态不是 WAITING"→ 返回错误。
```

## 七、与现有系统的对接

### 7.1 与 `proto/game.proto` 的关系

当前 proto 中 `RoomStatus` 枚举需扩展为 5 个值：

```protobuf
// 变更前（当前）
enum RoomStatus {
    ROOM_STATE_UNSPECIFIED = 0;
    ROOM_STATE_WAITING     = 1;
    ROOM_STATE_PLAYING     = 2;
    ROOM_STATE_FINISHED    = 3;
}

// 变更后（v0.8 实现时）
enum RoomStatus {
    ROOM_STATE_IDLE        = 0;  // ← 新增
    ROOM_STATE_WAITING     = 1;
    ROOM_STATE_PLAYING     = 2;
    ROOM_STATE_FINISHED    = 3;
    ROOM_STATE_DESTROYED   = 4;  // ← 新增
}
```

### 7.2 与 TimerManager 的关系

```
GameRoom 不自己管理定时器。
每个需要定时的场景向 TimerManager 注册一个定时任务：

  TimerManager::Schedule(delay_ms, callback)
  
  房间创建 → Schedule(5min, [this] { if (state_ == IDLE) Destroy(); })
  进入等待 → Schedule(10min, [this] { if (state_ == WAITING) Destroy(); })
  进入结算 → Schedule(30s,  [this] { if (state_ == FINISHED) Destroy(); })
```

### 7.3 与 RoomManager 的关系

```
RoomManager 持有所有活跃房间的 map<room_id, GameRoom*>。
  
  GameRoom::Destroy() 的最后一步：
    → RoomManager::RemoveRoom(room_id_)
    → 清理自身资源
```

## 八、面试要点

这一层能聊的核心话题：

1. **为什么用状态机而不是标志位**：状态互斥、转换可审计、非法操作在进入时就被拒绝
2. **超时策略的设计权衡**：为什么 IDLE 是 5 分钟、WAITING 是 10 分钟？—— 无科学标准，工程折衷。关键是**留有扩展点**（时长可配置），面试时能讲出为什么选这个数字
3. **并发模型**：单线程 EventLoop + 状态机 = 天然的线程安全。对比"加锁"方案：性能更好、无死锁风险、调试更简单
4. **状态机与协议的关系**：每个状态对应一组合法的消息类型。WAITING 状态下收到 `FrameInputReq`（帧输入）应直接拒绝——状态机帮你过滤非法协议
