# 帧同步全流程测试报告

> 版本：v0.9  
> 日期：2026-07-17  
> 测试文件：`tests/test_frame_sync_flow.cpp`

---

## 一、测试目标

模拟 3 个客户端走完完整的帧同步流程，记录各阶段 CPU 耗时，验证系统开销是否可接受。

## 二、测试场景

| 参数 | 值 |
|------|-----|
| 玩家数 | 3（p1 向右 / p2 向下 / p3 向上） |
| 帧率 | 20 fps（间隔 50ms） |
| 总帧数 | 60 帧（模拟 3 秒对局） |
| 环境 | WSL2 localhost，单线程 |

## 三、各阶段耗时

| 阶段 | 耗时 | 占比 |
|------|------|:--:|
| 匹配/创建/加入/开始 | 0.664 ms | 93.9% |
| 帧同步初始化 | 0.001 ms | 0.1% |
| 帧同步运行（60 帧） | 0.043 ms | 6.1% |
| 停止游戏 | 0.000 ms | ~0% |
| **总耗时** | **0.707 ms** | 100% |

## 四、帧同步核心指标

| 指标 | 值 |
|------|------|
| Tick 总耗时（60 帧） | 21.5 μs |
| Tick 平均耗时 | 0.4 μs/帧 |
| Tick 最大耗时 | 0.7 μs |
| 输入收集总耗时 | 16.7 μs |
| 输入收集平均耗时 | 0.3 μs/帧（3 玩家） |
| 输入收集最大耗时 | 0.9 μs |

## 五、延迟分析

```
理论帧间隔（20fps）      50,000 μs
实际 Tick 执行时间        ~0.4 μs
输入收集时间              ~0.3 μs
─────────────────────────────────
CPU 计算开销             < 1 μs（理论间隔的 0.002%）
```

**结论**：帧同步核心逻辑（Tick + 输入收集）的 CPU 开销不到 1 微秒，对 50ms 的帧间隔来说完全可忽略。系统的实际帧同步延迟将**几乎完全由网络 RTT 决定**，而非服务端计算。

## 六、阶段占比分析

房间创建/匹配阶段占据了总耗时的 93.9%（主要是 RoomManager 的 map 操作和状态转换）。帧同步初始化（分配 3 个 unique_ptr + 设置回调）几乎零开销。

## 七、当前局限与后续补充

1. **本测试为单进程 localhost**：所有耗时仅为 CPU 计算，不包含网络 RTT。真实多玩家场景下，延迟将由 `max(所有客户端 RTT)` 主导。
2. **无 GPU 渲染**：客户端渲染延迟不在测试范围内。
3. **单线程执行**：服务端为单线程 EventLoop，Tick 在 IO 线程内执行，无锁开销。
4. **建议后续补充**：
   - 增加玩家人数至 10/50/100，观察 tickLogic 耗时增长曲线
   - 加入丢包模拟，测试 CatchUp 追帧的额外开销
   - 跨机器部署 client↔server，测量端到端 RTT + 帧同步延迟

## 八、运行方式

```bash
cd build && make test_frame_sync_flow -j$(nproc) && ./test_frame_sync_flow
```
