# 游戏匹配系统设计：ELO、队列和超时放宽

> 本文记录 TinyRPC v0.10 匹配系统的实现过程，包括 ELO 评分、匹配队列、分差放宽和匹配成功后的自动化流程。  
> 项目仓库：[github.com/Archer11-q/tinrpc](https://github.com/Archer11-q/tinrpc)

---

## 为什么需要匹配系统

做完房间服务器和帧同步之后，玩家面临一个问题：怎么找到实力相近的对手？让玩家手动挑选房间不是不行，但对于竞技游戏来说，自动匹配是基础体验。v0.10 的匹配系统由三块组成：ELO 评分（衡量实力）、匹配队列（找到对手）、回调链路（匹配后的自动化）。

## EloCalculator：最多 30 行的公式

ELO 的核心就两个公式：

```
E_A = 1 / (1 + 10^((R_B - R_A) / 400))    // A 的期望胜率
R_A' = R_A + K * (S_A - E_A)              // 赛后新评分
```

400 是一个经验常数：高 400 分意味着对低分选手的期望胜率约 91%，"实力强 10 倍"。K 因子控制单局分数变化幅度——我们用 32，这是国际象棋的标准值，适合初始阶段的分数快速收敛。

实现极其精简：`CalcExpected` 一行公式，`UpdateRating` 一行公式，总计不到 10 行有效代码。但细节藏在边界里：同分期望 0.5，弱胜强加分远多于强胜弱（鼓励挑战），这些都在测试里逐项验证。

## MatchQueue：为什么不用 priority_queue

这个决策值得多写几句。`std::priority_queue` 是匹配队列的直觉选择——名字里就有"队列"。但深入匹配需求后，三个致命缺陷暴露出来：

**第一，无法找最近邻居。** 匹配需要"找分差最小的对手"——这是邻近搜索。堆只暴露堆顶（极值），玩家 1500 分想找最近对手，堆给不了答案。要遍历所有元素才能找到，退化到 O(n)。

**第二，无法随机离队。** 玩家取消匹配时要删掉该条目，堆不支持 `erase`。只能额外维护"已删除集合"做惰性清理，徒增复杂度。

**第三，`vector` + 二分是更好的选择。** 匹配池规模通常在 10~100 人，用 `std::vector` 保持 ELO 升序排列，`lower_bound` 二分查找插入位置；找对手时从自己的位置向两侧扫描，找到分差最小且在放宽范围内的玩家。O(n) 扫描在百人级别完全不构成瓶颈——我们实测 60 帧帧同步的 Tick 只花 0.4 微秒，匹配算法同理。

## 分差放宽：线性模型比分级更灵活

刚入队时，分差阈值是 100——只允许实力非常接近的玩家匹配。但玩家不应该永远等下去。

我们没有用"50→2s→100→5s→200"的分级策略，而是选择了线性的 `CurrentEloRange(waited_sec)`：

```cpp
range = elo_range_init + elo_range_expand * waited_sec;
// 初始 100，每秒放宽 20 → 5秒后 range=200
```

线性模型的优势在于配置灵活：改两个参数就能调节激进程度，不需要修改代码逻辑。测试里通过 sleep(600ms) 验证了放宽链路——刚入队时分差 100 > 范围 50 无匹配，600ms 后范围涨到 110 匹配成功。

## 匹配成功后：自动化流水线

匹配完成不是终点。`MatchCallback` 在配对上触发，自动执行：创建房间 → 双方加入 → 发送 `MatchFoundNtf`（含房间 ID 和 30s 确认超时）→ 启动超时定时器。

超时未确认时，房间销毁、双方按原分数重新入队——整个流程无需人工干预。断连清理也挂在这个链路上：`CancelMatch` 只是 `LeaveQueue` 的别名，在 EPOLLRDHUP 断连回调中调用，保证"死玩家不占队列"。

## 写在最后

v0.10 的 33 项匹配测试覆盖了从 ELO 计算到断连清理的全部路径——包括 3 人入队中间断连后剩余 2 人自动配对的极端场景。匹配系统本身不复杂，复杂的是它如何和已有系统（房间、广播、断连清理）无缝合流。`GameService` 作为集中入口，现在一个 `./rpc` 就能启动完整的匹配→房间→帧同步服务端。
